# Enhance Mode

"Send that Henrique goal to Enhance Mode." Enhance Mode turns a goal from the running career into a photorealistic press photograph. It runs the [match-stills](match-stills.md) process as one job: the replay's player positions and ball, the kits both teams wore, the installed face portraits, a low goal-line camera, and a review of every visible player before the image is shown.

The image is generated by the user's own Codex CLI on their ChatGPT plan. Enhance Mode holds no API key and reads none. The game is read and never written.

## Requirements

- Football Manager 27 running with the career loaded, and the reader able to attach.
- The Codex CLI, signed in with ChatGPT: `codex login`, then "Sign in with ChatGPT". `fm-enhance doctor` checks this.
- Optional: an installed facepack under the game's `graphics` folder. Without one, likeness has no reference.
- Optional: screen-recording permission for the process that runs the job, so it can photograph the replay. Without it, kits come from the club's stored definitions, which may not be the kit worn in that match.

## Use

From an MCP client (Claude, ChatGPT, pi-fm), ask for it in words. The client calls `fm_enhance_goal` with part of the scorer's name, or with nothing for the goal on screen, and polls `fm_enhance_status`. The job takes several minutes.

From a shell:

```bash
.venv/bin/python -m fm_live_mcp.enhance doctor
.venv/bin/python -m fm_live_mcp.enhance start --scorer Henrique
.venv/bin/python -m fm_live_mcp.enhance start        # the goal the match review is showing
.venv/bin/python -m fm_live_mcp.enhance status
```

`start` first looks at the replay open in the game. If that match has a goal by the named player, it is the match; with no name, the goal is the one the replay cursor is on, from ten seconds before it to twenty after. Otherwise `start` uses the most recent retained match with a goal by that player. `--match-key` names an exact match and `--event-id` an exact goal.

The game decodes a goal's frames only while its replay plays them, and FMCP cannot seek the replay. So the order that gives the best photograph is: start the job, then play the goal. The job watches for `--wait-seconds` (default 20, at most 300), reads each frame of the goal as it passes and photographs the game window while the goal is on screen. A goal the game has already shown leaves one frame behind, the ball in the net, and a job started afterwards uses that frame. Jobs live in `FMCP_ENHANCE_DIR`, or `~/Pictures/FMCP 27 Enhance` when that is unset. Each job is a folder; the finished photograph is `packet/goal.png` and `packet/index.html` shows it beside the original replay, the recorded positions and the provenance.

For another photograph of the same goal, reuse its evidence:

```bash
.venv/bin/python -m fm_live_mcp.enhance start --from-job 20261113-202838-luiz-henrique-v-villa \
  --direction "camera behind the keeper"
```

Direction may change camera, framing, light and mood. It never moves a player or the ball, changes a kit or replaces an identity.

## What the job does

| Stage | Result in the job folder | Source |
| --- | --- | --- |
| capture | `capture.json` | Retained shots of the match, club kits, scorer appearance, stadium |
| goal | `job.json` → `event` | The verified goal matching the scorer, goal number or event |
| frames | `frames/replay-TICK.json`, `sequence.json`, `screenshot.png` | Decoded replay frames of the goal's tick interval and the frame after it, read while the replay plays; a screenshot of the game window taken with the replay cursor on the goal |
| references | `references.json` | The screenshot, then portraits of the scorer and the players nearest him, by exact PERSON mapping |
| numbers | `numbers.json` | The squad number each player of the depicted frame holds now, read from his person record. Refused when the game has another career open |
| packet | `packet/` | The match-stills packet with the chosen camera and its guide drawing |
| generate | `packet/generation/`, `packet/goal.png`, `packet/goal.review.json` | Codex generates, inspects, corrects and records the review; FMCP validates it and attaches |

Each stage is skipped when its result exists, so a job continues from where it stopped: `fm-enhance resume JOB`, or `fm_enhance_goal` with `job_id`.

## States that need the user

| State | Meaning | What to do |
| --- | --- | --- |
| `capture_needed` | The game is closed, or none of the goal's replay frames is in the game's cache | Play the goal in the match review, then resume. For the strike itself, resume first and play the goal while the job watches |
| `choose_goal` | No goal or several goals match | Resume with an `event_id` from `goal_choices` |
| `codex_needed` | Codex is missing or not signed in with ChatGPT | `codex login`, then resume |
| `review_failed` | No candidate passed the review gate in this run | Resume for another correction turn; rejected candidates stay in `packet/generation` |
| `interrupted` | The run stopped before finishing | Resume |

The game keeps the frames around its replay cursor and, for a goal it has shown, the frame after the goal's interval. The job cannot seek the replay. That is why `capture_needed` asks for the goal to be played. `--allow-no-replay` continues from the shot origin alone; the result then has no decoded positions for the other players and no chosen camera.

## Camera, goal and numbers

The camera is a low photographer's position on the edge of the pitch, and the first choice is the press photograph from behind the play: a long lens on the scorer and the ball, a few players filling the frame, and the goal and its net across the background. Every two units of both touchlines and every four of the far goal line is tried. A position qualifies when the goal or its net lies behind at least 0.6 of a frame that holds the scorer and the ball with 1.4 either side (never narrower than 4.8), when the sight line does not pass through the net, and when the camera is within 70 of the scorer. Of those, the job takes the one where a nearer player covers the scorer least. In this view the scorer is usually seen from behind, with his number.

When no position puts the goal behind the play, the camera goes to the attacked goal line or a touchline of the attacked half and takes the narrowest lens that holds the scorer, the ball and the middle of the goal, among positions where no nearer player stands within 0.45 of the line to the scorer or 0.3 of the line to the ball. The choice and its measurements are in `scene.json` under `camera.selection`.

The prompt states how large a standing player is in the frame, and that a long lens at that distance keeps every player sharp. It also says what each player in the frame is doing. `sequence.json` records each player's movement per tick across the frames either side of the depicted one, and the prompt turns that into a direction and a rate for each player, names the scorer's marker (the nearest opponent within 1.2) and the goalkeeper, and forbids a row of upright figures. Movement is read; jumps, arms and where a head is turned are reconstruction. The review fails players who stand evenly spaced and upright with nobody contesting or watching the ball.

The camera guide draws the goal (posts 7.32 apart, bar 2.44 high, a net 2.0 deep), the goal line, the six-yard box, the penalty area and the penalty spot from the Laws of the Game, on the goal line of the replay positions. The prompt gives the projected places of the posts and requires the goal, its net and the lines in the photograph. The review fails a photograph with no goal or net, or with the goal on the wrong side of the players. The game's own goal and net model is not decoded.

Squad numbers come from the running game: the `Psnu` value of each player's person record, accepted only when both the record's index and its unique ID are the player's. The prompt lists the numbers of the players in the camera's view: large on the back of a shirt turned to the camera, small on the front of the shorts of a player facing it, none on a shirt front. The review fails a wrong number. These are the numbers held on the read date; the number worn in the match is not decoded separately. When the game cannot be read the photograph is made without numbers, as before.

## Action phase

A frame inside a goal's tick interval can show the ball arriving, at the scorer, or already on its way to goal. Pairing an arriving ball with a shooting follow-through was the error that stalled the first Luiz Henrique still. `sequence.json` orders the captured frames by the ball's distance from the scorer and labels each one `incoming`, `nearest_to_strike`, `strike_or_earlier`, `outgoing`, `in_net` or `unresolved`. The job depicts the first frame after the ball leaves the scorer toward the attacked goal, or failing that the frame nearest the strike, or failing that the ball in the net. `in_net` means the ball's decoded position is past the attacked goal line; it is the frame the game keeps after the goal's interval. The prompt states the depicted phase and the pose it permits. A screenshot taken at another tick supplies kits, stadium and identities, never the pose.

The labels come from ball-to-scorer distance at adjacent cached frames. They do not decode the contact instant, the shooting foot or a trajectory.

For a headed goal the sequence also records `strike`: the frame with the ball nearest the scorer, when the ball is within 1.0 of his position, and the ball's height in it. That height sets how far the scorer is off the ground. The camera guide draws a standing figure 1.8 tall, so a ball met at 1.7 or below leaves him standing, a ball met at 2.4 lifts him 0.7, and no figure is lifted more than 0.8. The prompt states the height, forbids a leap higher than it needs, and says the ball in the depicted frame is measured from the grass as the players are. With no frame near the strike the height is unknown, and the scorer is drawn standing. The review fails a header whose ball is level with the scorer's waist or legs, or whose pose is a kick or a volley.

## The Codex step

FMCP runs `codex exec` in the packet folder with write access limited to that folder, `image_generation` enabled, and `OPENAI_API_KEY` and `CODEX_API_KEY` removed from its environment. `fm-enhance doctor` and the job both refuse a Codex that is signed in with an API key. Codex reads `visual-review.md`, generates from `goal.request.json` with the built-in image tool, inspects the candidate, corrects it with edit passes (at most five generations a run), writes the selected image to `generation/final.png` and completes the review template for that exact image.

FMCP then validates the review against the hashes of the image, the prompt and the scene, and attaches the image only if every player and scene check passes. A refused review goes back to the same Codex thread once with the reason. The event stream of each turn is kept as `codex-N.jsonl`.

The review is a recorded judgement by the model that generated the image. It is not proof of likeness, and it does not prove that the pixels match the decoded positions.

## What is decoded and what is not

The [evidence contract](match-stills.md#evidence-contract) of match stills applies unchanged. In short: scorer, side, body part, shot origin, player XY and ball XYZ at cached frame endpoints come from the game. Camera, lens, poses, crowd, light and weather are chosen. The kit worn in a match is not decoded; it comes from the replay screenshot when one was taken. The screenshot is kept only if the replay cursor was on the goal when it started and no more than three seconds past it when it finished; FMCP does not check what the picture shows. Squad numbers are read as [above](#camera-goal-and-numbers); names on shirts and the shooting foot are not decoded.
