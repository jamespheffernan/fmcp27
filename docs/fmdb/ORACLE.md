# Differential oracle: generic reader against the existing tools

Generated by `scripts/fmdb_oracle.py`. Game date 2030-12-10; seed 1; records per sample {'player': 129, 'staff': 50, 'club': 51, 'competition': 50, 'stadium': 50, 'city': 50, 'currency': 173}; 674.8 s; 33,628 VM calls.

Statuses per (record, field): `match`; `mismatch`; `generic-unavailable` (the VM could not produce a value, or the getter did not claim the key); `tool-unavailable` (tool field absent or null while the generic reader has a value). A tool null against a generic null counts as a match. A mismatching record is re-read once before it is recorded.

## Method

For each sampled record the harness calls the existing tool (a `Bridge` method; the call and JSON path are in `fm_live_mcp/fmdb/oracle_map.py`) and reads the mapped editor code through `PropertyVM.get_property` (database view, reader thread). Tool references for random records are minted by registering the record in the Bridge's own reference table with the same decoders the finders use; every compared value then comes from the tool's normal `get_*` path. Reads are not atomic: a mismatching record is re-read (tool and VM, pages dropped) once before it is recorded, and the count recovered by that retry is kept in `report.json`. Random samples are seeded.

Rules:

* `exact`: integers/bools equal
* `string`: strings equal (generic null = empty)
* `empty_as_null`: tool null or empty equals generic empty
* `int_tol`: integers within `tol`
* `float32`: float32 bit-exact, else within `rel`
* `date_iso`: generic SI date ISO string equals the tool date string
* `fifths_raw`: stored byte 0-100 shown as max(1, (raw+2)//5)
* `direct_raw`: stored byte equals displayed value (direct mode)
* `blob_byte`: displayed attribute equals byte 1 of the 4-byte DATA blob
* `enum_code`: native enum integer equals the tool native_code
* `enum_label`: tool label equals the editor enum label for the generic integer (case/punctuation folded)
* `ref_name`: generic record reference resolved to the target record and its name compared
* `ref_uid`: generic record reference unique id equals the tool native_id
* `full_name`: first + second name (or common name) equals the tool full name
* `display_name`: common name, else full name, equals the tool display name
* `list_len`: generic list length equals the tool count
* `bool`: booleans equal
* `index_name`: generic integer database index resolved in another table and its name compared (folded)
* `presence`: tool count > 0 equals presence of the generic record/list
* `unset`: equal, or tool and generic both unset (tool 0/-1, generic null)
* `date_unset`: dates equal; tool null equals generic null or 1900-01-01 (not specified)

## Mismatches

### M1. different semantics (both defensible)

The Pcon property (0x1509140) returns -1 when primary slot 21 reports an injury record and slot 23 (the most days still out over the injury vector) is above 0; otherwise it returns slot 138 (stored int16 +0x254). So -1 is the game's own answer for a player who is out injured. The tool returns the stored value without that rule; the stored value is compared as condition_stored (extras.DERIVED) and agrees.

## Limits of this comparison

* Both readers read live memory; neither is an independent ground truth. Agreement shows two decoders reach the same value; disagreement is classified from the code paths, not from the game UI. No UI comparison was made.
* Families outside the list above are not compared: languages, local regions, weather, injuries as records, media sources, stadium changes, fixtures, stages, standings, registrations, tactics, training, transfers, match data.
* The sample is a seeded random draw from one save (Newcastle United, December 2030): the managed squad plus random records. Rare shapes (negative potential, dynamic expiry, basic contracts, virtual players) are barely or not sampled, and virtual players are not sampled at all (the tools support them only partially).
* The record handle for random records is registered in the Bridge reference table by the harness (see Method); the tools' own finder-to-ref path was used only for the managed squad.
* `Pcjo`, `injr`, `Papr` and `DELE` are not editor fields; they were taken from the tools' own research notes or found by case variation and kept only where they agree with the tool on the sample.
* `staff.contract.club_name` shows no mismatch in the full run but the live test sample hit the same B-team case as `player.club.*` (a staff member at `Les Voltigeurs de Châteaubriant 2`), so it is not pinned.
* Float comparisons are bit-exact on float32.
