# FM live investigation

## Coach a halftime adjustment

For a halftime or in-match decision, work from the going-in setup, score/time and first-half pattern already supplied. Label these as user-supplied observations. A fresh live read can replace a supplied detail only when it verifies the same fixture and current match period; a career date, editable tactic or completed-match total alone cannot establish halftime context. If no supported live halftime feed is available, say so once and coach from the supplied scenario rather than delaying for a retrospective match analysis. Ask at most one short question when an absent fact would materially change the immediate choice; a full intake form is unnecessary.

Recommend one or two concrete changes to the known setup. For each, name the phase, affected player/unit and playable instruction or role adjustment; explain the football mechanism and the cost elsewhere. Use verified game labels when available, otherwise describe the football action without inventing a UI label. Preserve the rest of the plan so the user can judge the intervention. A new formation or substitution needs a specific reason; check current readiness before recommending a named substitute.

Give a short 55–60-minute checkpoint tied to the reported pattern: what should visibly improve, what would show the change is failing, and when to revert or make the next small adjustment. Keep historical context separate from first-half evidence and future evaluation. Present the recommendation as a bounded tactical test, not a guaranteed best change, and distinguish proposed instructions from changes actually applied.

Completion: the answer identifies its evidence source, gives at most two immediate changes with mechanism and trade-off, and specifies the next observation and response without requiring a lengthy form.

## Compare recorded match periods

For a post-match question about halftime changes, bind the exact fixture date, ordered teams, competition and result. Use recorded half counters or source-verified named period intervals for that fixture. Assign attempts to a half only when the tool verifies both the period boundaries and their shared event-clock domain; preserve boundary ties, crossing events and extra-time uncertainty. Event order, sorted raw clock values, coordinates and changes of attacking ends are not period proof and must not be used to reconstruct halves. If that proof is unavailable, report the available whole-match figures and mark both halves unknown. A change in chances describes the observed match; attributing it to an instruction needs evidence of the actual change and still does not establish causation.

For half-by-half pass accuracy, resolve the exact retained fixture and query `fm_report_retained_pass_network_by_period`, including when an observed run supplies only completed passes. Check its verified period coverage before declaring attempts unavailable. Calculate accuracy from attempted and completed counts for the same fixture, side and period, keeping retained and observed provenance explicit. If verified period coverage is unavailable, keep whole-match passing separate and mark half accuracy unknown.

Completion: each reported half has authoritative period evidence, or remains explicitly unknown; no inferred boundary supplies a numerical half table.

## Start from the running career

For other unqualified career questions, including “my save”, read the running game. Use the dated archive workflow only for an explicitly requested or agreed file, backup, saved snapshot or offline catalog. A date in a fixture or player question can be investigated in the running career. If attachment fails or a field is unavailable, report the gap. For a historical match question, use discoverable captured match sources when they cover the requested fixture; keep their dated provenance separate from the current game.

Call `fm_status`, then `fm_attach`, then `fm_get_save` using the returned session ID. Establish the supported build, loaded career, managed club and current in-game date before giving live advice. Pi exposes these tools through `mcp__fm_live__`.

Reuse an attached session within the current Pi process. Start a fresh attachment after resuming a conversation, restarting the reader or loading another save. If a tool reports an expired session/reference or changed save, attach again and repeat discovery; an old opaque reference is not a stable entity ID. Include the in-game date when freshness matters.

This disables only its automatic period and spatial observation stores and their context/index writes; verify both returned capture reasons are `disabled_by_request`. It leaves the match-read source checks intact and is not a no-host-writes guarantee for other tools. If the option is absent, report the capability gap before using a default that persists observations.

Complete this step when the records identify the requested snapshot or live career, or the reader gives a specific reason it cannot read that source.
